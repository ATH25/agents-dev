# Coder Crew Requirements

## 1. Project Overview

- **Project name:** Coder Crew (`coder`)
- **Business objective:** Build a CrewAI-based coder AI project that accepts a coding assignment, solves it in Python inside a sandbox, runs the solution to check its output, and reports the code together with a summary of the work.
- **Application purpose:** Automate a single Python coding assignment through one configured CrewAI agent (`coder`) executing one configured task (`coding_task`).
- **High-level scope:** Refine the existing scaffold generated by `crewai create crew coder` by defining the agent and task in `agents.yaml` and `tasks.yaml`, the agent's model, the `{assignment}` input, the persisted task output, and the sequential crew configuration described in `requirement-draft.md`.

This document refines only the capabilities stated in `requirement-draft.md`. Recommendations, assumptions, and unresolved design choices are listed separately in Section 6 and are **not** approved requirements.

Status definitions:

- **Completed:** implementation is present and verified by repository inspection.
- **Pending:** implementation is absent, incomplete, or not yet verified.

## 3. Detailed Requirements

### 3.1 FR-02: Define the Coder Crew

**Business objective:** Give the project a single, clearly defined coding assistant and a single coding job, so that a coding assignment can be handed to the crew and the result is saved as a readable report.

**Functional description:** The crew's agent and task are described in two configuration files, `agents.yaml` and `tasks.yaml`, which the owner named in the draft. The crew has one agent, the Coder, and one task, the coding task. The assignment text is supplied when the crew is started and is inserted into the agent's goal and the task's instructions.

#### FR-02.1: Coder agent definition

The crew shall have exactly one agent, `coder`, with:

| Field | Required content (draft wording) |
|-------|----------------------------------|
| Role | The role of this agent is to code. Use Python as the coding language. |
| Goal | To code a given task. You use your sandbox tools to achieve this assignment: `{assignment}`. Write a Python file in the sandbox directory to achieve this assignment. Then run it to check the output. |
| Backstory | You are an expert Python coder who is good at coding. You are very thorough in your work and make sure that the code is well-structured and easy to understand. |

#### FR-02.2: Coder agent model

The `coder` agent shall use the model `openai/gpt-5.4-mini`. The owner named this model in the draft, so it is a business constraint.

#### FR-02.3: Coding task definition

The crew shall have exactly one task, `coding_task`, carried out by the `coder` agent. Its instructions are: "To code a given task. You use your sandbox tools to achieve this assignment: `{assignment}`."

#### FR-02.4: Task result and saved output

- The coding task's result shall contain the code for the given task and a summary of what the agent did to achieve the assignment.
- The result shall be saved to `output/code-task-output.md`.
- The draft's "expected output format" field is blank. No structure beyond "code plus summary" is required (see Q-05).

#### FR-02.5: Assignment placeholder

The agent's goal and the task's instructions shall both contain the `{assignment}` placeholder, so the assignment supplied at start-up appears in both. How the assignment is supplied is part of FR-07, not FR-02.

#### Business rules and constraints

- The draft lists only the `coder` agent and the `coding_task` task. No other agent or task is part of the approved crew, and the scaffold's example research agents and tasks are removed.
- The model, the placeholder name, and the output file path are mandated by the owner.
- Sandbox tools are mentioned in the agent's wording. Providing them is FR-05, not FR-02.

#### Assumptions and open questions

- A-02, A-03, A-04, and A-05 (Section 6.1) apply.
- Q-05 (output format) is open. The current configuration uses only the draft's wording.
- Until `crew.py` is updated to match the new agent and task names (task T-016, Phase P-04), the crew cannot be started. FR-02 is fully verified only after that.

### 3.3 Python file creation and execution — FR-05

- The generated solution shall be a Python source file.
- The file shall be written in a sandbox directory, not in an arbitrary location.
- The agent shall run the file and use the result to check its output.
- The sandbox mechanism, directory, filename, and execution limits are not specified by the draft (see Q-01 to Q-04, Q-06).

### 3.4 Inputs — FR-07

- Input key: `assignment` (string, non-empty).
- Consumers: `coder.goal` and `coding_task.description`.
- The source of the value (CLI, prompt, fixed value, trigger payload) is not specified (see Q-03).

### 3.5 Crew configuration — FR-08

The crew shall be constructed with:

| Setting | Value |
|---------|-------|
| `agents` | `self.agents` (the agents registered from the configuration) |
| `tasks` | `self.tasks` (the tasks registered from the configuration) |
| `process` | `Process.sequential` |
| `verbose` | `True` |
| `memory` | `True` |
| `tracing` | `True` |

## 5. Constraints and Dependencies

### 5.1 Approved constraints (from the business draft)

- CrewAI and the existing `coder` scaffold must be used.
- Agents and tasks are defined in `agents.yaml` and `tasks.yaml`.
- Python is the coding language for generated solutions.
- The `coder` model identifier is `openai/gpt-5.4-mini`.
- The input placeholder is `{assignment}`.
- The task output path is `output/code-task-output.md`.
- The crew runs sequentially with verbose output, memory, and tracing enabled.

### 5.2 Dependencies

- `pyproject.toml` declares Python `>=3.10,<3.14` and `crewai[tools]==1.14.1`.
- The project has no local virtual environment. The parent repository's shared `.venv` (Python 3.12) contains `crewai` 1.14.1 but not `crewai-tools`, so it does not fully satisfy the `crewai[tools]` declaration. The runtime that will execute this project is not verified.
- The configured OpenAI model requires a valid `OPENAI_API_KEY` (the parent repository's `.env.example` provides the template).
- FR-05 depends on a sandbox capability that can write and run a Python file. No such capability is configured today.
- FR-08 `memory=True` may depend on an embedding provider and its credentials.
- FR-08 `tracing=True` may depend on CrewAI tracing configuration or authentication.

## 6. Assumptions and Open Questions

### 6.1 Assumptions (used for planning only; not requirements)

- A-01: The classic YAML plus `@CrewBase` scaffold is retained, because FR-02 explicitly requires `agents.yaml` and `tasks.yaml`.
- A-02: "Build agents.yaml and tasks.yaml" means replacing the scaffold's example research agents and tasks, not adding to them.
- A-03: The task key is `coding_task`. The draft's heading says `code`, but `coding_task:` is the YAML-shaped key in the draft.
- A-04: "The code" in the expected output means the Python source produced for the assignment. The Markdown output file is separate from the executable `.py` file.
- A-05: No additional agents, tasks, tools, output formats, or user interfaces are approved.

### 6.2 Open questions requiring approval

| ID | Question | Affects |
|----|----------|---------|
| Q-01 | **Sandbox mechanism:** Which sandbox should the agent use? Options include CrewAI's built-in code execution (`allow_code_execution=True` with `code_execution_mode="safe"`, which requires Docker and is marked deprecated in CrewAI docs), a CrewAI tool, or a custom restricted tool. | FR-05 |
| Q-02 | **Sandbox directory:** What exact directory is the "sandbox directory" for generated Python files, and should files be kept after the run? | FR-05 |
| Q-03 | **Assignment input source:** Should `assignment` come from a command-line argument, interactive prompt, environment/config value, trigger payload, or a fixed development value in `main.py`? | FR-07 |
| Q-04 | **Generated filename:** Is the Python filename fixed, derived from the assignment, or chosen by the agent? | FR-05 |
| Q-05 | **Expected output format:** The draft leaves this blank. Should `output/code-task-output.md` follow a set Markdown structure, or include the captured execution output? | FR-06 |
| Q-06 | **Execution limits and failure behavior:** What timeout, network, and filesystem limits apply, and what should be written to the output if the code fails or times out? | FR-05, FR-06 |
| Q-07 | **Memory scope:** Are CrewAI default memory settings acceptable, and is memory expected to persist across runs? | FR-08 |
| Q-08 | **Tracing destination:** Is default CrewAI tracing acceptable, or must traces go to a specific CrewAI account or service? | FR-08 |
| Q-09 | **Retained entry points:** Should the scaffold's `train`, `test`, `replay`, and `run_with_trigger` entry points stay supported (and therefore receive `assignment`), or only `run`? | FR-07 |
| Q-10 | **Unnumbered requirements:** FR-05, FR-07, and FR-08 were created by an AI agent before RDDW was adopted and have no owner-numbered source in the draft (RDDW §3.2). Should they become owner-approved FRs, or sub-requirements of an existing or future FR? | FR-05, FR-07, FR-08 |

### 6.3 Recommendations (pending approval; not requirements)

- R-01: Approve a restricted sandbox contract (allowed directory, timeout, resource limits, network policy) before enabling execution of generated code.
- R-02: Define a fixed Markdown structure for the output file with sections for code, execution result, and summary.
- R-03: Keep credentials in `.env` (not in source control) and validate model access before an end-to-end run.
